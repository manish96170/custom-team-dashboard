# TUI Screen Guide

A step-by-step, screen-by-screen walkthrough of the dashboard's terminal UI: for each action
(keypress, click, or chat message), what you see before and after. This is the "click X, see Y"
guide the design docs don't give you — `FLOWS.md` §5 has the reference *table* of keybindings,
`PLAN.md` has the *design*; this doc has the actual rendered screens.

## How this doc stays honest

Every screen below is **not a mockup** — it is copied verbatim from
`supervisor/tui/evidence/01-demo-frames.txt`, which is generated by running the real TUI against a
real supervisor, a real event pump, and a real control socket (a fake harness stands in only for
the model process itself, so no tokens are spent). Regenerate it with:

```
node supervisor/tui/capture-frames.mjs > supervisor/tui/evidence/01-demo-frames.txt
```

**When you add or change a TUI action, add a scene for it in `capture-frames.mjs` and re-run that
command, then update this doc's frame for it.** A screen here that no longer matches the real
output is worse than no doc at all — this file is meant to be re-generated alongside the code, not
written once and left to drift, the same "looking is one command" reasoning `capture-frames.mjs`'s
own header comment gives for why it exists as a real script rather than a one-off.

Frame size throughout: 118 columns × 30 rows (`COLUMNS=118 LINES=30` if you want to match it in a
real terminal). Every screen is exactly this size; a smaller terminal shows a "terminal too small"
message instead (`layout.js`'s `MIN_COLS`/`MIN_ROWS`).

## Try it yourself

```
node supervisor/tui/cli.js --demo
```

Self-contained — no daemon, no tokens, no setup. It starts a supervisor, a fake harness, two teams,
three tasks and five workers in-process, and points the TUI at them over a real socket. Everything
in it is real except the harness, so what you see is the actual layout driven by actual supervisor
state. `node supervisor/tui/cli.js` (no `--demo`) attaches to a real running supervisor instead —
you'll need `boot()` to have written `owner.token` first (`HANDOFF.md`'s "run the tests first"
section explains the token file if you haven't seen it).

## Layout, at a glance

```
+- TEAMS ---------------------------------------------------------------+
|  [chip] [chip] ...                                                    |
+- REQUESTS (only when something is pending) ---------------------------+
+- REVIEW bar (only when the selected task has a review in flight) -----+
+-----------+-------------------------------------------------------------+
| TREE      |  PANE AREA (1 or 2 panes, side by side)                   |
+-----------+-------------------------------------------------------------+
| footer: keybindings for the current state, + a status line when set  |
+-------------------------------------------------------------------------+
| chat bar: always resident, target is CTO or a specific worker         |
+-------------------------------------------------------------------------+
```

Three rows are **conditional** — TEAMS, footer and chat are always there; REQUESTS only appears
with pending requests, and REVIEW only appears when the selected task has a review in flight.
That's why several screens below have different total heights for the pane area even though the
frame itself is always 30 rows.

command** — the chat box would be useless otherwise (imagine typing "help" and it toggling

## Every action, at a glance

The full reference table — every binding, situation, and result — lives in `FLOWS.md` §5 and is
kept in sync with `tui/state.js`'s `keyToAction`/`applyAction` (the two pure functions this whole
guide is a rendering of). This doc doesn't duplicate that table; it shows what the table's outcomes
actually look like on screen. If a key isn't covered by a numbered step above, check §5 first —
then check the gap list below, in case it's documented but not actually wired yet.

## Known gaps — documented as a feature, but not (yet) real

Cross-checked against the actual code on 2026-09-10, re-checked 2026-09-11 (steps 16-20 added the same
day) — worth re-checking this list whenever this doc is regenerated, since the whole point of grounding
it in real frames is to stop drift like this from going unnoticed:

- **`v` (effort/variant picker)** — `FLOWS.md` §5 documents it ("opens a quick effort/variant
  picker scoped to that one run"). There is no `v` case anywhere in `tui/state.js`'s `keyToAction`.
  Not built.
- **`g` (grouped/split toggle)** — `state.js` does flip a `state.grouped` flag on `g`, but
  `layout.js` never reads `state.grouped` anywhere. The key does something to state and nothing to
  the screen — wired half-way.
- **Requests panel buttons (Accept/Decline/Complete/Team Requests), including step 19's Request
  Detail view's own `[a] Accept`/`[d] Decline`** — the panel's small button row is drawn but still
  not clickable (`layout.js`'s hit target says so plainly). The detail view's Accept/Decline ARE
  wired as far as the UI goes (step 20) — pressing them closes the view and sets a status line — but
  there is still nothing on the other end: no wire command turns a request into a real task. Same
  underlying gap as always (Slack inbound, which is what would create a real request to accept, is
  still backlog), just now reachable from two places in the UI instead of one.
- **Chat commands ("hide `<team>`", "move `<name>` -> `<team>`", "onboard `<harness>`",
  "@`<nickname>` `<task>`")** — `FLOWS.md` §5 lists these as chat-driven typed commands. What's
  actually built: the chat bar sends whatever text you type verbatim as a `tuiChat` wire command
  (`tui/app.js`) — real, tested, and it does round-trip to the supervisor. What's *not* built is
  anything on the other end that parses "hide Vite Migration" into `hideTeam` — that's the CTO's
  job (PLAN.md §16), and the CTO is ROADMAP Phase 8, not built yet. Today, typing a command into
  chat gets you `sent to cto` and nothing happens, honestly, rather than a fake success.

None of these are secretly broken — they're accurately reflected in `ROADMAP.md`'s phase status if
you check it. They're listed here because this doc's whole premise is "what you actually see when
you press a key," and the honest answer for these four is "not this yet."

1. Add or change a scenario in `supervisor/tui/capture-frames.mjs` (it's a straightforward
   sequence of `app.handleKey(...)` / `app.handleClick(...)` / direct `app.state = {...}` calls,
